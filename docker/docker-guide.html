Container Docker Compose Secrets

Docker Guide

Docker Desktop unter Windows einrichten, Container verstehen und Anwendungen samt Daten und Secrets nachvollziehbar betreiben.

Docker verpackt eine Anwendung mit ihren benötigten Bibliotheken und Einstellungen in eine einheitliche Laufzeitumgebung. Damit kann dieselbe Anwendung auf dem eigenen Rechner, im Team und später auf einem Server möglichst gleich laufen. Auf Windows nutzt Docker Desktop für Linux-Container in der Regel WSL 2 im Hintergrund.

Das macht Docker besonders praktisch für lokale Datenbanken, Testumgebungen, Web-Apps und mehrere zusammengehörige Dienste. Ein Container ist aber kein magischer Sicherheitskasten: Rechte, Updates, Backups und ein gutes Secrets-Konzept bleiben weiterhin nötig.

Was sind Container – und wofür sind sie nützlich?

Ein Container ist eine laufende Instanz eines Images. Das Image ist die Vorlage; der Container ist die tatsächlich gestartete Anwendung. Container teilen sich nicht einfach wahllos den eigenen Rechner: Prozesse, Netzwerk und Dateisystem werden weitgehend getrennt. Sie sind trotzdem keine vollständigen virtuellen Maschinen und keine absolute Sicherheitsgrenze.

Einheitliche Umgebung

Alle im Team starten dieselbe Node-, Python-, Datenbank- oder Webserver-Version statt „bei mir geht es doch“.

Lokale Dienste

PostgreSQL, MongoDB, Redis oder Meilisearch lassen sich ausprobieren, ohne sie dauerhaft in Windows zu installieren.

Tests & CI

Tests laufen gegen eine vorhersehbare Umgebung und können später in einer Pipeline nachgebaut werden.

Aufräumen

Ein Versuch ist mit Container und Netzwerk schnell entfernt. Dauerhafte Daten gehören bewusst in ein Volume.

BegriffBedeutungBeispiel
ImageSchreibgeschützte Vorlage für einen Container.mongo:8
ContainerAusführbare Instanz eines Images.eine gestartete MongoDB
VolumeVon Docker verwalteter, dauerhafter Speicher außerhalb des flüchtigen Container-Dateisystems.Datenbankdaten
NetzwerkVerbindung zwischen Containern und – nur wenn veröffentlicht – zum Host.Web-App → Datenbank
ComposeEine compose.yaml beschreibt mehrere Dienste, Volumes und Netzwerke gemeinsam.App + DB + Cache

Wichtige Grenze: Ohne Volume verschwinden Änderungen im Container-Dateisystem beim Entfernen des Containers. Volumes machen Daten haltbar, verschlüsseln sie aber nicht automatisch.

Docker Desktop unter Windows per Hand einrichten

Für die meisten Einzelpersonen ist Docker Desktop mit Linux-Containern und WSL 2 der unkomplizierteste Weg. Aktuelle Anforderungen und den offiziellen Installer beschreibt die Docker-Dokumentation für Windows.

  1. Voraussetzungen prüfen: Windows aktuell halten; bei Bedarf Hardware-Virtualisierung im BIOS/UEFI aktivieren. Für Linux-Container ist WSL 2 der normale Weg.
  2. PowerShell als Administrator öffnen und WSL installieren bzw. aktualisieren.
  3. Neu starten, falls Windows dazu auffordert. Das ist nach einer ersten WSL-Installation normal.
  4. Docker Desktop von docker.com laden, installieren und den WSL-2-Backend verwenden. Die Installation pro Benutzer ist für die meisten privaten Geräte ausreichend.
  5. Docker Desktop über das Startmenü öffnen und warten, bis die Engine läuft. Bei der ersten Ausführung Lizenzbedingungen bewusst prüfen.
  6. In einer neuen PowerShell testen.
# Diese Befehle in einer als Administrator gestarteten PowerShell ausführen.
wsl --version
wsl --install
wsl --update
# Nach der Docker-Desktop-Installation in einer neuen PowerShell testen.
docker version
docker compose version
docker run --rm hello-world

Erwartetes Ergebnis: hello-world lädt bei Bedarf ein kleines Test-Image, startet es und entfernt den Test-Container danach wieder. Erst wenn dieser Test funktioniert, lohnt es sich, ein eigenes Compose-Projekt zu starten.

Einrichtung per PowerShell-Skript

Ein Skript kann die wiederholbaren Schritte vorbereiten. Es kann jedoch weder Hardware-Virtualisierung im BIOS sicher einschalten noch einen erforderlichen Neustart überspringen. Die folgende Variante nutzt bewusst den offiziell heruntergeladenen Docker-Desktop-Installer statt einen Installer aus einer unbekannten Quelle.

  1. Docker Desktop von der offiziellen Docker-Seite herunterladen und die Datei im Downloads-Ordner belassen.
  2. Die folgende Datei als install-docker.ps1 speichern.
  3. PowerShell als Administrator öffnen und das Skript ausführen. Falls wsl --install einen Neustart verlangt: neu starten und das Skript danach erneut ausführen.
# install-docker.ps1
# Als Administrator ausführen. Der Docker-Installer wurde vorher bewusst
# von https://www.docker.com/products/docker-desktop/ heruntergeladen.
$ErrorActionPreference = "Stop"

$principal = [Security.Principal.WindowsPrincipal] [Security.Principal.WindowsIdentity]::GetCurrent()
if (-not $principal.IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)) {
    throw "Bitte PowerShell als Administrator starten."
}

# Richtet WSL beim ersten Mal ein. Windows kann danach einen Neustart verlangen.
wsl --install
wsl --update

$installer = Join-Path $env:USERPROFILE "Downloads\Docker Desktop Installer.exe"
if (-not (Test-Path -LiteralPath $installer)) {
    throw "Docker Desktop Installer.exe wurde im Downloads-Ordner nicht gefunden."
}

Start-Process -FilePath $installer -Wait -ArgumentList @(
    "install",
    "--user",
    "--backend=wsl-2"
)

Write-Host "Docker Desktop über das Startmenü öffnen und danach testen: docker run --rm hello-world"

Die Option --user installiert Docker Desktop für das aktuelle Benutzerkonto. Wer Software zentral für mehrere Windows-Konten verwaltet, sollte stattdessen die Installationsmodi und Rechteanforderungen in der offiziellen Docker-Dokumentation prüfen. Eine Lizenzannahme gehört nicht unsichtbar in ein Beispielskript.

Die ersten Docker-Befehle

Mit dem folgenden kleinen Webserver lässt sich der Lebenszyklus eines Containers gefahrlos üben. Das Image wird beim ersten Start automatisch geladen.

# Einen nginx-Webserver im Hintergrund starten.
docker run --name demo-web --detach --publish 8080:80 nginx:alpine

# Im Browser öffnen: http://localhost:8080
docker ps
docker logs demo-web

# Sauber beenden und den Container entfernen.
docker stop demo-web
docker rm demo-web
BefehlWofür?
docker psLaufende Container anzeigen.
docker ps -aAuch gestoppte Container anzeigen.
docker image lsLokale Images anzeigen.
docker volume lsVorhandene Docker-Volumes anzeigen.
docker network lsDocker-Netzwerke anzeigen.
docker compose up -dAlle Dienste der aktuellen compose.yaml im Hintergrund starten.
docker compose logs -fLogs der Compose-Dienste fortlaufend ansehen.
docker compose downContainer und das Standardnetzwerk eines Compose-Projekts stoppen und entfernen.

Vorsicht mit docker compose down -v: Das -v entfernt zusätzlich die zugehörigen Volumes. Bei einer Datenbank bedeutet das normalerweise: Test- oder Anwendungsdaten werden gelöscht.

Compose, Daten und Netzwerke

Für eine einzelne Testanwendung genügt oft docker run. Sobald mehrere Teile zusammenarbeiten, wird Docker Compose übersichtlicher. Eine compose.yaml beschreibt dann Dienste, Ports, Volumes und Netzwerke in einer versionierbaren Datei.

1. compose.yamlBeschreibt die gewünschte Anwendung.
2. docker compose upErzeugt Netzwerk, Volumes und Container.
3. DienstnameContainer sprechen intern über Namen wie db.
4. portsNur bewusst veröffentlichte Ports sind vom Host erreichbar.
5. VolumeWichtige Daten überstehen Container-Neustarts.
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./site:/usr/share/nginx/html:ro

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: beispiel
      POSTGRES_USER: beispiel
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:

secrets:
  db_password:
    file: ./secrets/db_password.txt

In diesem Beispiel ist postgres_data ein benanntes Volume: Daten bleiben erhalten, wenn der Datenbank-Container neu erstellt wird. Der Webserver darf das lokale Verzeichnis site nur lesen (:ro). Der Datenbank-Port wird hier bewusst nicht veröffentlicht; andere Dienste desselben Compose-Projekts können ihn über db:5432 trotzdem erreichen.

Port-Regel: Eine Datenbank, Vault oder Admin-Oberfläche sollte nur dann per ports: veröffentlicht werden, wenn sie wirklich vom Host erreichbar sein muss. Für einen lokalen Dienst ist eine Bindung wie 127.0.0.1:27018:27017 sicherer als eine Freigabe für das gesamte Netzwerk.

Secrets: Docker nutzen, ohne Schlüssel zu verraten

Passwörter, API-Keys, Zertifikate und private Schlüssel sind Secrets. Ein Container speichert sie nicht automatisch sicher. Insbesondere gehören echte Secrets niemals in ein Dockerfile, ein Image, Git, Browser-Code oder eine öffentlich ausgelieferte Konfigurationsdatei.

Nicht soWarum problematisch?Besser
ENV API_KEY=... im DockerfileDer Wert kann im Image, in dessen Historie oder Registry landen.Secret erst zur Laufzeit gezielt bereitstellen.
Secret direkt in compose.yamlDie Datei wird häufig mit Git geteilt und landet leicht in Backups.Datei lokal ignorieren oder einen echten Secret-Manager verwenden.
Echtes Secret in .env committenGit-Historie ist schwer vollständig zu bereinigen..env ignorieren; nur eine leere .env.example committen.
Secret in Frontend-VariablenAlles, was zum Browser ausgeliefert wird, ist für Besuchende lesbar.Secret nur serverseitig verwenden.

Compose Secrets für eine lokale Linux-Container-Umgebung

Compose kann einem ausdrücklich berechtigten Dienst ein Secret als Datei unter /run/secrets/<name> einhängen. Das ist weniger fehleranfällig als eine Umgebungsvariable, die durch Debug-Ausgaben oder Unterprozesse sichtbar werden kann. Die Quelle bleibt bei lokalem Compose trotzdem eine Klartext-Datei auf dem eigenen Rechner – sie braucht also weiterhin Schutz und darf nicht in Git.

# .gitignore
secrets/
.env
.env.*
!.env.example
# Nur einen Fantasiewert verwenden – niemals einen echten Schlüssel in ein Tutorial kopieren.
New-Item -ItemType Directory -Force secrets | Out-Null
Set-Content -NoNewline -Path secrets/api_token.txt -Value "nur-ein-testwert"

docker compose up -d
docker compose logs secret-check
docker compose down
services:
  secret-check:
    image: alpine:3.21
    command: ["sh", "-c", "test -s /run/secrets/api_token && echo 'Secret-Datei ist vorhanden'; sleep infinity"]
    secrets:
      - api_token

secrets:
  api_token:
    file: ./secrets/api_token.txt

Was das leistet – und was nicht: Compose grantet den Zugriff nur dem gewählten Dienst; bei Linux-Containern wird die Datei im Container eingehängt. Die lokale Quelldatei ist dadurch aber nicht verschlüsselt, und ein Konto mit weitreichendem Zugriff auf Docker bzw. den Host ist keine unbeteiligte Person. Für Produktion gehören Rotation, Zugriffstrennung, Auditing und ein echter Secret-Manager dazu.

Für Swarm-Services gibt es zusätzlich Docker Swarm Secrets, die im Swarm verschlüsselt übertragen und gespeichert werden. Das ist ein anderer Mechanismus als die lokale Compose-Datei und gilt nicht für einzelne docker run-Container. Für Build-Zugänge sollten BuildKit-Secrets statt ARG oder ENV eingesetzt werden.

Praxisbeispiel: SecretsLab mit Vault und MongoDB

Das Repository Datenflix007/SecretsLab ist ein gutes Lernbeispiel dafür, wie Docker eine reproduzierbare lokale Laborumgebung starten kann. Es ist kein Docker-Swarm-Secrets-Beispiel und auch kein produktionsreifer Passwortspeicher.

Python-Labor

Fordert einen frischen DEK an und verschlüsselt einen Test-Key lokal mit AES-256-GCM.

→
Vault Transit

Ver- und entschlüsselt den Daten-Schlüssel (DEK); der Schlüssel zur Schlüsselverschlüsselung bleibt bei Vault.

→
MongoDB

Speichert Ciphertext, Nonce, verschlüsselten DEK und Metadaten – nicht den vollständigen Klartext-Key.

Docker Compose startet darin zwei voneinander getrennte Dienste: MongoDB und HashiCorp Vault. MongoDB nutzt ein benanntes Volume, während die Python-Anwendung und das Menü auf dem Host in einer virtuellen Python-Umgebung laufen. Die externen Ports sind auf 127.0.0.1 beschränkt, also nur vom eigenen Rechner erreichbar.

git clone https://github.com/Datenflix007/SecretsLab.git
cd SecretsLab
.\quickstart.bat

Voraussetzungen sind eine laufende Docker-Desktop-Engine mit Linux-Containern sowie Python 3.11 oder neuer. Das Quickstart-Skript startet Compose, wartet auf Vault, aktiviert die Transit-Engine, legt den Schlüssel user-secrets an und öffnet anschließend ein Terminalmenü. Verwende dort ausschließlich Fantasie- oder Testwerte.

Niemals mit echten API-Keys verwenden: SecretsLab nutzt absichtlich Vault im Dev-Modus – mit HTTP, bekanntem Root-Token, ohne produktive Vault-Persistenz und ohne MongoDB-Authentifizierung. Die Funktion get kann einen Test-Key im Terminal anzeigen. Nach einem Vault-Neustart können ältere MongoDB-Einträge wegen des verlorenen Vault-Schlüsselmaterials nicht mehr entschlüsselt werden.

Die Lehre aus dem Beispiel lautet nicht „Docker ist ein Secrets-Tresor“, sondern: Docker isoliert und startet die Bausteine reproduzierbar. Die Trennung zwischen verschlüsselten Daten in MongoDB und Schlüsselverwaltung in Vault entsteht durch die Anwendungskryptografie und Vault Transit. Wer Vault samt Root-Token kontrolliert, kann weiterhin entschlüsseln.

# Im SecretsLab-Ordner:
docker compose down     # Container stoppen; das MongoDB-Volume bleibt erhalten.
docker compose down -v  # Vollständiger Labor-Reset: auch Testdaten löschen.

Checkliste für eigene Projekte

Start

docker run --rm hello-world läuft erfolgreich und Docker Desktop ist bereit.

Daten

Datenbanken, Uploads und andere langlebige Daten liegen bewusst in Volumes oder einem externen Speicher.

Netzwerk

Nur nötige Ports sind veröffentlicht; sensible lokale Dienste binden an 127.0.0.1.

Secrets

Keine echten Werte in Git, Images, Dockerfiles, Browser-Code oder öffentliche Logs.

Produktion

Ein echter Secret-Manager, Rotation, Backups, Updates und minimale Berechtigungen sind geplant.

Aufräumen

down -v wird nur ausgeführt, wenn das Löschen der zugehörigen Daten wirklich beabsichtigt ist.
